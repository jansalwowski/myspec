# Resuming a Run

Read from SKILL.md Step 1 (Resume), at startup only, on the trigger SKILL.md gives. Never apply it mid-run: a `[~]` task there is one this session dispatched, and its worktree is live. `<plugin lib>` is the path SKILL.md resolves.

1. **Scan every task checkbox.**
   - `[x]` = already done — skip entirely
   - `[~]` = was in progress when the previous session stopped — unless its phase finished implementing (step 3) or the task is already committed (step 4), re-execute this task from scratch. When it ran in a worktree, first clear the stale one with `"<plugin lib>/task-worktree.sh" discard <slug>` (a no-op when none exists) — `create` refuses an existing slug, and the partial work never passed review. The slug is `<feature>-t<N>` for a parallel task, and `<feature>-p<N>` for a concurrent phase (parallel-phases.md), which then runs again from scratch, every task of it
   - `[ ]` = todo — execute normally
2. **Recover the run's state.** `BASE_SHA` comes from the `Base (feature)` entry, and for the phase being resumed, `PHASE_BASE` from its `Base (Phase N)` entry, so the phase review still spans the commits made before the restart. A plan from before these entries has none: take `BASE_SHA` from `git merge-base HEAD <integration branch>` and record the phase base afresh. `$STATE` is what `"<plugin lib>/implement-state.sh" init {feature}` prints. It names the main checkout's state directory from every checkout of the repository, so a run stopped in a worktree finds its packages, logs and stage stamps from the main checkout or from the worktree created again.
3. **A phase that finished implementing resumes where it stopped, never by re-executing its tasks** — its work is already on the feature branch, so re-implementing it would redo the phase on top of its own commits, and the review would span both copies. This needs the phase's `Base (Phase N)` entry from step 2. Read its stage stamps, `$STATE/phase-N.times`:
   - **last stamp `done`** — the review passed: finish 4e (flip the tasks to `[x]`), then 4f.
   - **last stamp `review` or `fix-R`** — resume at the phase review, SKILL.md Step 4 item (b) — not Step 4b, the milestone checkpoint: a fresh review over `PHASE_BASE`, passing the existing `$STATE/phase-N-verify.log`. A fix loop cut off mid-round starts over from that review's findings; the rounds its `Fix base (Phase N, round R)` entries log count toward the five. An interrupted fixer's uncommitted edits are part of the dirty tree Step 0 already had the user resolve: committed, the fresh review covers them; stashed, they are gone.
   - **last stamp `barrier`** — resume at Step 4a. A task worktree still present is merged, not discarded (the barrier starts only once every task is done), and a merge still in progress (`git rev-parse -q --verify MERGE_HEAD` exits 0) is finished first, as parallel-tasks.md resolves a conflict.
   - **a concurrent phase with no `barrier` stamp** — parallel-phases.md logs its `Base (Phase N)` only after the phase finished implementing, just before the merge, so that entry alone means the work is done. Finish the merge: a merge in progress is completed as above; a `<feature>-p<N>` worktree still in `git worktree list` is merged with `"<plugin lib>/task-worktree.sh" merge <feature>-p<N>`, not discarded. Then resume at Step 4a.

   Any other phase — no `Base (Phase N)` entry, or no stamps — re-executes its `[~]` tasks as step 1 says, apart from those step 4 finds committed. A `Base (Phase N)` entry with no `$STATE/phase-N.times` is a run from before stamps or a lost state directory: say so in one line, naming `$STATE`, before you re-execute.
4. **A `[~]` task already committed is not re-implemented.** A serial task commits from your checkout straight onto the feature branch, so a session that stopped between one task's commit and the phase review leaves that task `[~]` with its work done. For each `[~]` task of a phase that step 3 left to re-execute and that has a `Base (Phase N)` entry, run `git log --first-parent --format=%H --grep='^Plan-Task: <N>$' <PHASE_BASE>..HEAD` (`implementer-prompt.md` makes every task commit carry that line; `--first-parent` keeps out another feature's commits that a merge of the default branch brought in):
   - **exits 0 with a sha** — the task is committed. Do not dispatch it: it stays `[~]` and goes to the phase barrier and review with the rest, which verify it as they verify any task. Tell the phase reviewer that Task N was recovered from its commit with no implementer report, so its self-review is unproven. In workflow mode, leave it out of the workflow's `tasks` and set `phaseBase` to the current HEAD, as for a BLOCKED re-launch (workflow-args.md). When that leaves no task to dispatch, in either mode, launch nothing and go straight to the barrier, Step 4a.
   - **exits 0 with no output** — nothing committed: re-execute it as step 1 says. A parallel task's commits sit in its worktree until the barrier merge, so they never match here, and a run from before the `Plan-Task` line has none either.
   - **exits non-zero** — `PHASE_BASE` is not a commit (history was rewritten after it was logged): stop for the user. Never read it as "nothing committed".
5. **Find where to resume.** Start at the first milestone containing any non-`[x]` task — unless an earlier milestone, or any milestone when every task is `[x]`, carries `**Checkpoint probes:**` without a passing entry per probe; resume at the first such milestone's probe gate (Step 4b) instead. A passing entry is a `Probe` line with PASS (SERVED for a `D<n>` demo) or a `Waiver` line.

Step 0 still asks where to work, and Step 2 still runs: `implement-state.sh init` returns the same `$STATE` from any checkout, and the orchestration marker is set again for the new session.
