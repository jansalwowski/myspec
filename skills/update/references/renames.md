# Renamed entries (update Step 2)

A `files` or `rules` entry may carry `renamedFrom: "<old key>"`. It means the framework changed a file's name or location, and the project on disk still holds the old one. The old key is spelled as a `.myspec.json` `frameworkFiles` key (`rules/<name>` for a rule, bare for an `{aiDir}` file), so it may name the other block: `"renamedFrom": "rules/x.md"` on a `files` entry moves a rule into `{aiDir}`. Take the old and new destination from the row `node "<plugin lib>/manifest-keys.mjs" renames` printed for it; never derive one by hand. Before applying such an entry:

1. If the new destination exists → nothing to migrate; apply the entry normally.
2. If it does not exist and the old destination does → `git mv` (or plain move) the old file to the new destination, creating directories, **and** rename its `.myspec.json` `frameworkFiles` key from the old key to the new one if one exists, keeping any `pinned` value and hashes. Then apply the entry to the renamed file, so a `marker-merge` merges into the project's real content instead of a fresh copy. List it under `Renamed` in the Step 6 summary. The move and key rename stand on their own: finish and keep them even when the apply that follows cannot merge (a marker-less file goes to the marker-less choice in Step 3). Undoing the move leaves the doctor reporting `framework-renamed` forever, because that finding fires whenever the old file exists.
3. If neither exists → create from source as usual. If `.myspec.json` still carries the **old** key (a project that renamed by hand and pinned the old name so update would stop recreating it), drop that key and report "already renamed locally".
4. If **both** exist → the project renamed by hand before the framework carried the rename, or an earlier update installed the new file while a pin kept the old one. Never merge unasked: only the user knows which one their blueprints wrote to. For a `marker-merge` entry, show the project section of each (everything after `<!-- myspec:framework-end -->`) and offer to append the old file's project section to the new file's, then delete the old file and drop its key. When the old file has no end marker it has no project section, and is usually a redirect stub left as a workaround: show its full content and offer to delete it, or to append that content to the new file's project section and then delete it. For an `overwrite` entry neither file has a project section: show a diff of the old file against the new one and offer to move the old file over the new one (its key and pin renamed as in case 2, the content apply skipped when pinned), or to delete the old file and drop its key. Any accepted answer deletes the old file. On decline, leave both untouched and report it; the doctor keeps naming the pair as `framework-renamed` until one goes.

Skipping step 2 is what makes this dangerous: `overwrite`/`marker-merge` both treat a missing destination as "create from source", so the entry would land a *fresh empty-project-section* file beside the real one, and every blueprint that writes to the new name would write to the empty duplicate.

Never invent a `renamedFrom`; it comes from the manifest only. A pinned renamed entry is still renamed — move the file and the key, then skip the content apply. Run the renames before pin reconciliation, so the pins it reads already carry the new keys.
