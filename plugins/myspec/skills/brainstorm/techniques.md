# Brainstorm — Techniques & Rationale

Loaded on demand from `SKILL.md`. Read this when you need a technique for the current mode, when a mode's default isn't moving, or when you want the reasoning behind the facilitator stance. Don't force techniques — reach for one when the conversation needs it.

## Why the stance is what it is

A 1-on-1 AI brainstorm is structurally the *strongest* setup for the worst documented failure of group brainstorming — **production blocking** (people forget or suppress ideas while waiting their turn) simply doesn't exist when it's just you and the user. But it introduces, or re-creates, failures a group doesn't have. All four below **resist conscious correction**, which is why the stance handles them through behavior rather than by warning the user.

- **Anchoring.** Your first ideas and framing become a reference point that quietly collapses the user's solution space into yours — and anchoring persists even when people are explicitly warned about it. *Structural fixes:* if the user brought a seed, expand *theirs* before offering your own; when you do generate, span genuinely different categories; surface and vary the underlying assumptions, not just surface ideas; use "consider the opposite" (reverse brainstorming).
- **Sycophancy = groupthink at n=1.** A validating AI and the user form a two-person concurrence-seeking in-group; the documented antidote is a built-in critic, not a friendlier tone. Models also tend to *bury* disagreement under apology and praise. *Structural fixes:* take an adviser/critic stance, state the objection plainly and first, use neutral framing ("what are the weaknesses?") over leading ("this is good, right?").
- **Premature convergence.** Both parties want to settle fast; filling every silence with output also denies the user the incubation that aids divergence. *Structural fix:* hold divergence and judgment in separate beats, and announce the shift to narrowing.
- **Illusion of productivity.** A fluent list *feels* generative but is often low-variety and reproduces the obvious. Subjective satisfaction is a poor proxy for idea quality. *Structural fix:* optimize for *flexibility* (distinct categories) over *fluency* (raw count); push past the first answers.
- **The user free-riding on you.** The inverse of social loafing — the user disengages and lets you do the thinking, which kills the build-on loop and their ownership. *Structural fix:* regularly pull their instinct back in.

The two phases this all serves: **divergent** thinking (generate many, defer judgment, widen) and **convergent** thinking (narrow, evaluate, decide). The cardinal rule is to keep them in separate beats — never evaluate an idea in the same breath you generate it. Across the whole arc, a brainstorm tends to walk the two "diamonds": first diverge/converge on the *problem* (Frame), then diverge/converge on the *solution* (Generate → Sharpen).

## Technique menu by mode

### Frame — define the right problem

| Technique | When | How (1-on-1) |
|---|---|---|
| **How Might We** | A complaint or a pre-decided solution is masquerading as the problem | Rephrase as "How might we [action] for [who] so that [outcome]?" Generate several variants; not so broad it's unanswerable, not so narrow it bakes in the answer. |
| **Laddering** | Wrong altitude — too abstract or too detailed | Ladder *up*: "why does this matter?" Ladder *down*: "what specifically?" Find the level that suggests routes without dictating them. |
| **Five Ws (+H)** | Coverage check on a fuzzy space | Walk Who / What / When / Where / Why / How; the questions you *can't* answer mark where the real work or research is. |
| **Decomposition** | The space is actually several problems | Split into independent sub-problems, name their relationships, pick one to brainstorm first. |
| **Assumption surfacing** | Something feels off but unnamed | List what's being taken for granted; test the weakest. |

### Generate — produce options

| Technique | When | How (1-on-1) |
|---|---|---|
| **Diversity pressure** | First instinct for any generation | Literally aim for ideas "as different from each other as possible"; label your output as provocations, not picks. |
| **"What if…" branching** | Open the possibility space / story or design premises | Throw many "what if [context flips]?" provocations; on the one they react to, ask who/what/why and branch again. |
| **"What else?"** | Ideas feel generic/clichéd | Refuse the first answers; keep asking "what else?" — originality lives several answers in. |
| **Analogy transfer** | Need a genuinely fresh angle | "What domain solved a similar problem?" Import its structure ("how do bees coordinate? → …"). |
| **Multi-persona (parallel)** | Output is converging on one voice | Generate independently from a few *distinct* viewpoints (e.g., a skeptic, a newcomer, a domain expert). Ordinary, varied personas often diverge better than famous-genius ones. |
| **SCAMPER** | Improving an *existing* thing | Substitute, Combine, Adapt, Modify, Put to other use, Eliminate, Reverse — walk each lens. |
| **Constraints** | Output is vague or sprawling | Impose an arbitrary limit ("no dialogue", "ships this week", "≤2 words") — limits force specificity and paradoxically expand ideas. |
| **Worst possible idea** | Stuck, intimidated, or over-cautious | Deliberately generate terrible ideas, then invert them — lowers the stakes and unlocks the good ones. |
| **Naming sub-mode** | A name, tagline, label, API term | High volume of variants under explicit diversity pressure + voice personas + constraint games (alliteration, length). Judge on resonance/fit, not feasibility; don't over-analyze. |

### Solve — get unstuck

| Technique | When | How (1-on-1) |
|---|---|---|
| **5 Whys / root cause** | Always first in Solve | Ask "why is this happening?" on each answer, ~5 times, until the root cause surfaces. Do not generate fixes before you reach it. |
| **Reverse brainstorming** | Direct solutions are scarce | "How could we make this *worse* / guarantee failure?" then invert each answer into a preventive fix. |
| **First principles** | Inherited assumptions are constraining | Strip to fundamentals and rebuild without the assumptions you arrived with. |
| **Constraint removal** | The idea seems blocked | "If [the binding constraint] didn't exist, what would you do?" then work back toward feasibility. |

### Sharpen — pressure-test & decide

| Technique | When | How (1-on-1) |
|---|---|---|
| **Devil's advocate by severity** | Pressure-testing a leaning idea | Lead with the strongest objection, then work down by severity. State each plainly; don't soften. |
| **Pre-mortem** | Before committing | "It's a year out and this failed badly — why?" Harvest the failure causes into fixes or a go/no-go. |
| **Assumption audit** | A plan rests on beliefs | Enumerate the load-bearing assumptions; attack the weakest. |
| **Six Thinking Hats (black-hat focus)** | Want structured critique without chaos | Examine from one lens at a time — caution, benefits, facts, feelings — so critique is bounded, not scattered. |
| **Criteria-first + trade-off table** | Choosing among options | Surface the decision criteria *before* comparing; lay options against them; **don't generate new options** here. |
| **Steel-man each option** | Risk of a foregone conclusion | Argue the strongest case *for* each candidate before recommending one. |
| **MoSCoW** | Prioritizing | Must / Should / Could / Won't — forces explicit deprioritization. |

## Fine purpose → mode → guard

The four modes are coarse on purpose. When a session needs disambiguating, these are the seven underlying purposes the research distinguishes and where each lands:

| Purpose (what the user really wants) | Mode | Watch for |
|---|---|---|
| Frame / understand a fuzzy problem | **Frame** | premature solutioning |
| Generate options from scratch | **Generate** | mode collapse — the obvious five |
| Name / word / phrase something | **Generate** (naming sub-mode) | over-analysis, homogeneity |
| Solve a specific stuck problem | **Solve** | fixing the symptom, not the cause |
| Pressure-test / refine an existing idea | **Sharpen** | sycophancy |
| Decide between known options | **Sharpen** | generating *more* options instead of deciding |
| Plan / sequence an implementation | *hand off* → `/myspec:feature-plan` | re-opening settled decisions |

## Software brainstorms

When the brainstorm is shaping software:

- **Design for isolation and clarity.** Propose units that can each answer three questions: *what does it do, how do you use it, what does it depend on*. If a unit can't answer all three without referring to its internals, the boundary is wrong — narrow it before moving on. Smaller, well-bounded units are easier to reason about, edit reliably, and test independently.
- **Working in an existing codebase.** Explore the current structure before proposing changes, and follow existing patterns. Where existing code has problems that affect the work (a file that's grown too large, unclear boundaries), fold targeted improvements into the design — the way a good developer improves code they're working in. But don't propose unrelated refactoring; stay focused on what serves the current goal.
