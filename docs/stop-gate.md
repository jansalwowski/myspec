# Stop gate: requirements

The stop gate is two hooks. `mark-code-changed.sh` (PostToolUse) records what a session writes. `verify-before-stop.sh` (Stop) runs the checks in `.claude/verification.json` when the session changed code and blocks the stop on a failure. The Stop hook is a shim over `lib/stop-gate/`: `arm.sh` (which checkouts are armed, R1 to R3a, R5, R6), `provision.sh` (R8), `run.sh` (the per-check verdicts, the capped runner and the budget, R7, R8a, R11, R12, R13), `attribute.sh` (R4, R6) and `report.sh` (R9 and the decision). This file collects what the gate must do, from the issues that shaped it, so the next change is checked against all of them rather than the one in front of it. Design notes for single parts: `verify-check-escapes.md` (time cap and budget), README "Isolation" (linked dependency directories).

| R2 | A write in another repository or outside the checkout (a scratchpad, `/tmp`) does not arm this checkout's gate. Its final verification still gates. | #95, #254 |
| R7 | A check that hits the 120 s cap is reported as timed out, not failed. The cap bounds the hook's wait and kills the check's process group. Remote work gets the check's `cleanup`. The cap is never raised. | #115, #147 |
| R8 | A linked dependency directory whose lockfiles changed since provisioning, or whose link no longer points into the recorded source, blocks before any check runs. A directory provision did not link is doctor's finding, not the gate's. `worktree-provision.sh` records each link it makes, with its physical target and the SHA-256 of each lockfile that pinned it, in the worktree's `.claude/state/provision.json`, and each lockfile pattern that matched nothing, and each glob pattern, with a null hash; a lockfile counts as changed when its hash differs or it is gone in the recorded source or in the worktree, and when a null-hash pattern matches a file on either side that the record does not hash (a nested lockfile the branch adds after provisioning), and a link as moved when it no longer resolves to its recorded target (a task worktree's link into a controller worktree resolves on into the main checkout, so the target, not the source prefix, is what is compared). A tree whose root or nested link directory it cannot list counts as loading; a tracked file inside a directory to link (a `.gitkeep`) stops provisioning with the fix. | #94, #229, #222, #239 |

The forms are data in `lib/stop-gate/run.sh` (`CONTAINER_EXEC_FORMS`: `docker exec`, `docker compose exec`, `podman exec` and the like), matched as words with options allowed between them; nothing after `exec`, `-w` included, is read. A check with `runIn` (R12) is trusted to use the workdir the gate exports, and `setup-doctor` warns ahead of a stop about a container check without `runIn` and a `runIn` command that passes neither `-w`/`--workdir` nor `MYSPEC_CHECK_WORKDIR`. The refusal blocks, never warns through attribution, and does not apply in the main checkout or its own submodules. | #220, #250 |
| R9 | Memory and setup conformance errors block only when they are errors. Warnings, such as a duplicate ID on stale branches only, don't block. | #124 |
| R10 | One block per stop: the continuation after a block (`stop_hook_active`) is approved. A nested Claude Code session a check starts (`claude -p`, an eval runner) is approved at once without running anything: the gate exports `MYSPEC_STOP_HOOK_ACTIVE=1` to its checks, and the hook reads it from its own environment. | 4eb8ccb, #257 |
| R11 | A check with `paths` runs only when a file this session wrote in that checkout (the ledger's repo-relative paths, code or not) matches one of its globs; without `paths` it always runs. A required check skipped this way is named in the stop message, an approve included (a `systemMessage`), so the loosening is never silent. A `paths` that is not a non-empty list of usable globs is ignored, the check runs, and the message names it. The ledger misses writes it cannot see (`git revert` or `checkout`, `rm`, a code generator, a variable path), so a path git reports changed in that checkout also runs the check when it matches: uncommitted or untracked (`git status`), or changed against `$MYSPEC_BASE_REF` (R5). On a feature branch that includes the branch's earlier commits, so a check skips only when its globs match nothing the branch or the working tree changed. Glob semantics: see Per-check settings. The check gets those files as `$MYSPEC_SESSION_FILES`, relative to the directory it runs from: the checkout root, or its `cwd`. | #232, #255 |
| R12 | A check with `runIn` names a container in the top-level `containers` map (`{mountSource, mountTarget}`). The gate exports `MYSPEC_CHECK_WORKDIR`, where this checkout's `mountSource`, or the check's `cwd` under it, sits inside the container, and does not read the command for `-w` (R8a). When the checkout's `mountSource` is not under the main checkout's (a worktree outside the mounted directory), or the check's `cwd` is not under `mountSource`, the check is refused with "not visible inside the container" and never run. A `runIn` naming an undefined container, or a container without a repo-relative `mountSource` and an absolute `mountTarget`, refuses the check with its reason. Refusals block like R8a's. | #221, #250 |
| R13 | One time budget covers the whole stop: every check in every armed checkout, and their cleanup, 300 s by default and below the Stop entry's `timeout` (330 s in `hooks.json` and `templates/settings-hooks.json`; the harness default without one is 600 s; `verify-check-escapes.md`). `MYSPEC_GATE_BUDGET_SECONDS` lowers it and can never raise it. A check that would start after the budget ran out is not run; one running when it runs out is capped at what is left and reported as timed out. A check that did not run is not a pass: the stop blocks (or warns, during a feature-implement run, R6), and the message names the checks that ran and the ones that did not. Attribution never downgrades it. | #250 |

## Session writes (R1–R4)

Session state is one append-only file per session, `.claude/state/sessions/<session_id>.jsonl` in the main checkout, beside the session's live log. A repository whose main checkout git cannot name from a linked worktree (a bare clone with worktrees, a `--separate-git-dir` checkout) keeps it in its git common dir instead, `myspec-state/sessions/<session_id>.jsonl`, so every worktree of it shares one file (`session_home` and `session_dir`, which every writer and reader, `set-isolation.sh --show` included, goes through). `lib/session-event.sh` is its only writer and reader. Each line is one JSON event with `at` (epoch seconds): `write`, `verified`, `isolation` (`set-isolation.sh`), `implement` (R6) and `notice` (a one-time step was taken: `imported-implement`, below). Appends are single short `O_APPEND` writes, so concurrent subagents' lines don't interleave, and a reader skips a line that does not parse. The file is in the checkout, not `/tmp`, so `TMPDIR` does not matter: the hooks of one session agree on it whatever their environment.

`mark-code-changed.sh` appends one `write` event per written file: `{"t":"write","root":<checkout root>,"rel":<repo-relative path>,"kind":"code|file"}`. The root is the physical toplevel of the checkout holding the file, so a linked worktree and another repository each get their own events. The event goes to the state file of the main checkout of the file's repository (a submodule's goes to its superproject's), and only when that checkout, or the checkout holding the file, has a `.myspec.json` or a `.claude/verification.json`: a linked worktree whose branch adds the stop gate arms before the main checkout has it. A write into a plain clone nested in the cwd's checkout whose own repository has no config is filed in the cwd's state file under the clone's own root, and the gate verifies that root through the cwd's checkout as below; a write into an untracked repository outside the cwd's checkout is not recorded (R2). `verify-before-stop.sh` appends `{"t":"verified","root":<root>}` for each checkout once it has printed its decision; a run that dies before deciding (an `awk` that fails on a check's output under `set -e`, say) records nothing, so the checkout stays armed. A checkout is armed when a `code` write for its root comes after its last `verified` event, and every armed checkout that shares the cwd's git common dir is verified (R3a). An armed checkout nested inside the cwd's tree that is not a checkout of this repository, such as a submodule, is verified through the cwd's checkout, and the files written in it count as the session's there. Each check gets `$MYSPEC_SESSION_FILES`: the files this session wrote in that checkout, one path per line relative to the directory the check runs from (the checkout root, or its `cwd`), so a per-file linter can scope itself to them.

For a Write or Edit, the written file is the tool's `file_path`. For Bash, only the targets of the write are recorded: a redirect target, the operands of `tee`, `sed -i` and `perl -i` (`-i` anywhere among the options, the command called by any path), every operand of `mv`, the destination of `cp`, `rsync` and `install`, and the files `patch` edits and writes (`-o`). Before, every code path anywhere in a command counted once any segment wrote. A quoted literal path is read through the scanner's `keep` mode. A variable path stays invisible, and so do `git apply` and a script that writes from inside a heredoc. Relative targets resolve against the payload `cwd`, moved by a literal `cd` earlier in the command and restored when a subshell ends.

Every written file is recorded, code or not, because the ledger is also the attribution list: a `tsconfig.json` or `package.json` this session edited must count as its own.

What counts as code is `CODE_EXT` plus `hooks.markCodeChanged.extraCodeExtensions`, and a path matching a `hooks.markCodeChanged.ignorePaths` glob is recorded as `file` even when its extension is code, so generated output never arms the gate by itself (#231, `docs/project-settings-design.md`). Both are read through `lib/myspec-config.sh` from the checkout holding the written file, not the cwd's, falling back to its primary checkout when it has no `.myspec.json`. The globs are repo-relative and follow the `paths` rules under Per-check settings: one compiler, `lib/glob-regex.sh`, serves `ignorePaths`, `checks[].paths` and `isolation.provision.clean`. A default extension can't be removed; ignoring the paths that hold it does that. A malformed value falls back to the default and is named on stderr.

Subagents share their parent's `session_id`; their tool events add `agent_id` and `agent_type`, and the main session's carry neither (#225). The state file stays keyed by `session_id`, so a subagent's write arms the parent's gate and counts as the session's file, and a subagent reads its parent's isolation decision. A subagent's `write` event gains `"agent":<agent_id>`. In the session log a subagent's path is tagged `` - `path` (subagent <agent_id>, <agent_type>) ``, which is how session-complete keeps the controller's own edits apart from delegated ones.

The ledger outlives each run: the `write` events are the list of files the session wrote, which attribution reads on every run. Before the state file it was `/tmp/.myspec-session-writes-<session_id>`, one tab-separated line per write. For one minor release, the one that introduces the state file, the first read or write of a session whose state file does not exist yet imports that file once and renames it `.imported`, so a session running across the upgrade keeps its ledger; the next minor drops the import. The same release imports the 2.x markers the state file replaced, on the session's first read or write: a `.claude/state/implement-in-progress.json` no older than 8 h becomes an `implement` start dated its `started_at` (unless the session already has an `implement` event), and the session's own `.claude/state/isolation/<session_id>.json` becomes an `isolation` event dated its `decided_at`. The isolation marker is renamed `.imported`, fresh or not, so it is read once. The implement marker is per checkout, so it stays in place: each session imports it once, records a `notice` event (`imported-implement`) in its own file, and the marker expires by its 8 h age, so a session upgraded mid feature-implement keeps warning instead of blocking and a parallel session cannot consume it first. The empty `/tmp/.myspec-code-changed-<session_id>` marker before it is no longer read.

## Attribution (R4)

It applies per verified checkout, when its checks fail and the session is not in a feature-implement run. Let T be the files this session wrote in that checkout. Let F be the uncommitted and untracked files not in T, excluding `.claude/state/`.

1. F is empty: every uncommitted change is this session's. Block.
2. A failing check's output names a file in T: block. T is matched by basename, which errs toward blocking.
3. Every failing check names a file in F and none in T, and no check timed out: approve, and put the failures in a `systemMessage` for the user. F is matched by its full repo-relative path, or, for a check with a `cwd`, by its path relative to that `cwd` (a tool run from `api` prints `api/src/Foo.php` as `src/Foo.php`), which errs toward blocking.
4. Otherwise: block. The reason lists F and tells the agent not to edit those files to make a check pass.

**Known limits.** A Bash side effect (an install, code generation, a formatter), or a Bash write to a variable path, is not in T. When it lands in F, a failure that names only that file warns instead of blocking (rule 3). The block message in rule 4 says so. A change by this session that breaks a file another session has open also warns (rule 3): the failure is real, but the other session's gate owns it. Several sessions in one checkout can't be separated exactly. A worktree per session is the fix, and the warning says so.

**Not covered.** The memory and setup conformance gates are still armed by uncommitted changes under the memory tree or `.claude/`, not by this session's writes. Many of those writes come from lib scripts through Bash, which the ledger can't see.

## Per-check settings (R5, R7, R11, R12)

The gate reads `checks` and `containers` through `lib/myspec-config.sh`, the one settings reader (`docs/project-settings-design.md`), from the checkout whose `.claude/verification.json` is in use. The reader ships with the hook; when it or another lib the gate sources is missing, the gate blocks once with "myspec lib missing, run /myspec:update" and runs no check, rather than guess at the settings. A reader that is there and fails (a jq older than 1.6, which lacks `--rawfile`) also blocks, with the reader's own error and what to check instead of the update advice, and the checkout stays armed until it reads. Order per required check: `paths` first (a skipped check is never refused), then `cwd`, then `runIn` or the R8a refusal, then the run.

**Globs (`paths`).** Each glob is matched against each session file as a repo-relative path. These are the semantics doctor validates (#233):

- A glob matches the whole path from the repository root. `*.php` matches only a file at the root; `**/*.php` matches one at any depth.
- `*` matches any run of characters within one path segment, and `?` matches one character other than `/`.
- `**` as a whole segment matches zero or more segments: `api/**` is everything under `api/`, and `a/**/b.ts` matches `a/b.ts` and `a/x/y/b.ts`. `**` inside a segment (`a**b`) is a plain `*`.
- A trailing `/` means everything under it (`api/` is `api/**`), and a leading `./` is dropped.
- Every other character is literal, including `[`, `{` and `\`. There are no classes and no braces: list two globs instead of `{api,worker}/**`.
- An empty glob, an absolute one, or one with a `..` segment is unusable.

The set matched is every file the session wrote in the checkout, not only those since the last run. A check that failed before still runs after the session moves on to other directories.

**Directory (`cwd`, #250).** A check runs from the root of the checkout being verified, or from its `cwd`, a repo-relative directory of that checkout (not of the main checkout), so a package's check needs no `cd` in its command. A leading `./` and a trailing `/` are dropped, and `.` and `""` are the root. A `cwd` that is not a string, is absolute, or has a `..` segment, checked again after each strip (`.//api` is `/api`), is ignored: the check runs from the root and the stop message names the setting, as for `paths`. `rel_dir` in `hooks/verify-before-stop.sh` does this for `cwd` and a container's `mountSource` alike, and doctor's `setting-dir-missing` applies the same rules. A directory that does not exist in the verified checkout (a worktree made from a base that did not have it yet) refuses the check as not run, "not a test failure", which blocks like R8a's refusals and is never downgraded by attribution; doctor reports it first in the checkout it runs in (`setting-dir-missing`). `$MYSPEC_SESSION_FILES` is relative to the `cwd`: with `cwd` `api`, `api/a.php` is `a.php` and `web/a.ts` is `../web/a.ts`, so every path opens from where the check runs. `paths` still matches repo-relative paths. `git diff --name-only` prints repo-root-relative paths from any directory, so a `cwd` check whose `diffCommand` passes its output to a tool adds `--relative` (paths relative to the `cwd`, and only those under it), or `cd`s to the root first (`cd "$(git rev-parse --show-toplevel)"`).

**Workdir (`runIn`).** Let M be the main checkout (`checkout_facts` in `lib/hook-core.sh`; for a submodule, its superproject's main checkout plus the submodule's path) and C this checkout. A checkout whose repository has no main checkout git can name (a bare repository's worktree) refuses a `runIn` check. `MYSPEC_CHECK_WORKDIR` is `mountTarget` plus the path of `C/mountSource` under `M/mountSource`, plus the check's `cwd` relative to `mountSource`; a `cwd` outside `mountSource` refuses the check. With `mountSource` `.` that is `mountTarget` in the main checkout and `mountTarget/.claude/worktrees/<name>` in a worktree under the default `isolation.worktreeRoot`. With `mountSource` `api`, a worktree's `api/` is not under the main checkout's `api/`, so only the main checkout is visible. A polyglot pair:

```json
{
  "containers": { "api": { "mountSource": ".", "mountTarget": "/srv/app" } },
  "checks": [
    { "name": "API tests", "command": "docker compose -p myapp exec -w \"$MYSPEC_CHECK_WORKDIR/api\" api composer test", "runIn": "api", "paths": ["api/**"], "required": true },
    { "name": "Web typecheck", "command": "npx tsc --noEmit -p web", "paths": ["web/**"], "required": true }
  ]
}
```

The PHP suite runs in the container and the TypeScript check on the host, each only when the session wrote under its directory. `-p myapp` pins the compose project to the one started from the main checkout: without it compose names the project after the directory it runs in, and the gate runs the command from the worktree root, so from `.claude/worktrees/<name>` it looks for a project `<name>` and finds no running service. A top-level `name:` in the compose file pins it too, and so does exec on the container by its name (`<runtime> exec <container>`). The command is the project's, so `podman exec`, `nerdctl exec` or `kubectl exec` work the same way.

**Containers in a linked worktree (R8a).** A container exec runs in the container's working directory, which mounts the checkout the container or compose project was started from, usually the main checkout. From a linked worktree it either finds no running service or verifies the main checkout's tree. So a check without `runIn` whose command contains a declared exec form is refused there, and a check with `runIn` is trusted to pass `-w "$MYSPEC_CHECK_WORKDIR"` (or to use the variable some other way). The gate reads nothing else of the command: `setup-doctor` parses the exec options instead (short-flag clusters included: `-Tw <dir>` sets the workdir, `-ew` is `-e w`) and warns about a `runIn` command that passes neither `-w`/`--workdir` nor `MYSPEC_CHECK_WORKDIR`, which would verify the container's default workdir. A worktree outside the mounted directory cannot be verified in the container at all; create it under the main checkout's `isolation.worktreeRoot`, or run the tool on the host.

**A check's fields.** Each entry in `checks` has a `name`, a `command` and `required`; only a required check runs. The rest are optional: `cwd`, `paths`, `runIn` (above), `diffCommand` and `cleanup` (below). A `notes` string at the top level is free text for the people editing the file; the gate never reads it. `templates/verification.json` points here instead of repeating this section.

**Diff-scoped command (`diffCommand`, R5).** Give a check a non-empty `diffCommand` when its plain `command` already fails on the default branch. The gate runs `diffCommand` instead, with `$MYSPEC_BASE_REF` exported as the merge base with the default branch (on the default branch itself, the range is what is uncommitted). Scope the command to that range and guard it against an empty file set, since most tools given no files check everything: `files=$(git diff --name-only --diff-filter=ACMR "$MYSPEC_BASE_REF" -- '*.<ext>'); [ -z "$files" ] || <linter> $files`, with the extension and linter of the stack (`*.py` and `ruff check`, `*.ts` and the project's lint script, `*.php` and its static analyser). When no default branch resolves (no remote and no `main` or `master`), the plain `command` runs.

**Cleanup (`cleanup`, R7).** A check killed at its cap, or at the gate budget (R13), takes only its local client with it: work it runs in a container or on another host (`docker exec`, `kubectl exec`, `ssh`) keeps running. Such a check needs a `cleanup` command. The gate runs it after a timeout only, with the same `$MYSPEC_CHECK_RUN_ID` the check saw, under its own cap (30 s, lowered with the check cap). Have the check record its remote PID in a file named after `$MYSPEC_CHECK_RUN_ID`, and have `cleanup` kill that PID's process group; the README shows the pattern for a compose service, and `verify-check-escapes.md` gives the design.
